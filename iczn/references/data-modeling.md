# Data Modeling — Names, Taxa, and Nomenclatural Acts

This file is not a chapter summary; it is the schema-design guidance that makes the rest of this skill usable by a database builder. It exists to prevent one specific, expensive, irreversible mistake: collapsing **name** and **taxon** into a single table with one `status` column that mixes nomenclatural and taxonomic status. Every other reference file in this skill cites this file when it says "see data-modeling.md" for the concrete schema treatment of a rule.

## 1. The three-layer separation

The Code itself keeps three different kinds of thing apart, even though everyday taxonomic language ("the name of the species") blurs them. A database that does not keep them apart will eventually silently overwrite a fact with an opinion.

**Nominal taxon / name** — the nomenclatural object. Its original spelling, authorship, publication, date, the rank-group (family/genus/species) it was established in, and its name-bearing type are fixed by the single act of establishment and never change because someone reclassifies the animal ([Arts. 10–20](https://code.iczn.org/chapter-4-criteria-of-availability/article-10-provisions-conferring-availability/) govern availability; [Art. 61](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-1) governs typification; [Art. 50](https://code.iczn.org/authorship/article-50-authors-of-names-and-nomenclatural-acts/) governs authorship). Availability, once acquired, is permanent — invalidity as a junior synonym, junior homonym, unjustified emendation, unnecessary substitute name, or a suppressed name does not undo it ([Art. 10.6](https://code.iczn.org/chapter-4-criteria-of-availability/article-10-provisions-conferring-availability/#art-10-6)). The exact *rank* a name is used at may later be raised or lowered without touching authorship, date, or type ([Art. 23.3.1](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-3-1), [Art. 61.2.2](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-2-2)) — so "current rank" belongs one layer up, not here.

**Taxon concept** — the taxonomic hypothesis. A circumscription (which name-bearing types fall inside a boundary) asserted by a named person, at a named date, in a named publication. Validity, synonymy, and rank *placement* live here. [Art. 23.1](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-1) states the priority rule, but which nominal taxa an author has chosen to unite under it is an opinion, reversible by the next author ([Art. 23.3.6](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-3-6)).

**Nomenclatural act** — the events: establishment, type fixation, lectotype/neotype designation, emendation, replacement, new combination, First Reviser action, reversal of precedence, Commission ruling. Each act has an author, a date, a publication, and an effect. Modelling acts as first-class records — not just mutating a field on the name — is what makes the nomenclatural history reconstructible and auditable, which is the whole point of a Code built around priority and traceability ([Art. 23.6](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-6)).

**The test.** For any datum you are about to add a column for, ask: *would this change if a taxonomist changed their mind, without any new nomenclatural act being published?* If yes, it is not a property of the Name — it belongs on a TaxonConcept or a ConceptRelationship, asserted by somebody, dated, sourced. If the only way it can change is via a new published act (a new type designation, a new combination, a Commission Opinion), it belongs on a NomenclaturalAct, not as a silently-overwritten scalar.

## 2. Entity-by-entity model

### Name
The nominal taxon as established. **Attributes:** original spelling ([Art. 32](https://code.iczn.org/formation-and-treatment-of-names/article-32-original-spellings/) "original spelling", not detailed here — see `references/07-formation-spelling.md`), group (family/genus/species — fixed at establishment), rank-within-group at establishment, gender (genus-group names), formation type (noun/adjective/genitive per [Art. 11.8](https://code.iczn.org/chapter-4-criteria-of-availability/article-11-requirements/#art-11-8)–[11.9](https://code.iczn.org/chapter-4-criteria-of-availability/article-11-requirements/#art-11-9)), availability flag with the citing Article if unavailable, the generic name it was *originally* combined with if species-group ([Art. 11.9.3](https://code.iczn.org/chapter-4-criteria-of-availability/article-11-requirements/#art-11-9-3)), a coordinate-group identifier (§3.1), FKs to the establishing NomenclaturalAct, the current name-bearing TypeFixation, and the Publication. **Relationships:** established by one NomenclaturalAct; has one authoritative TypeFixation; may be one of several coordinate Names sharing that act; may be the subject of many later new-combination acts. **Justifying Articles:** 10–20 (availability), 21 (date), 50 (authorship), 61 (typification).

### TypeFixation
The event (or, before 1931, the automatic consequence) that ties a Name to its name-bearing type. **Attributes:** type category at the moment of this record (holotype/syntype/lectotype/paralectotype/neotype for species group; type species for genus group; type genus for family group — see `references/16-species-group-types.md`, `references/15-genus-group-types.md`, `references/14-family-group-types.md`), method (original designation, monotypy, tautonymy, subsequent designation), validity flag (only one lectotype designation is ever valid per name — [Art. 74.1.1](https://code.iczn.org/types-in-the-species-group/article-74-name-bearing-types-fixed-subsequently-from-the-type-series-lectotypes-from-syntypes/#art-74-1-1)), FK to the performing NomenclaturalAct, FK to the Name it types, FK to a TypeSpecimen (species group) or to another Name (genus/family group — the type is itself a nominal species or genus, [Art. 61.1.2](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-1-2)). **Relationships:** many TypeFixation rows may exist per Name across history; exactly one is current. **Justifying Articles:** 61.1 (the type concept, recursive by rank group), 63 (family-group types fixed automatically — not subject to subsequent fixation), 74 (lectotype from syntypes).

### TypeSpecimen
The physical (or, rarely, illustrated-only) specimen. **Attributes:** repository, catalog number, collecting data — deliberately *no* type-category column (§3.8). **Relationships:** referenced by zero, one, or many TypeFixation rows over time (a syntype referenced once, later superseded by a lectotype-designating TypeFixation that references the same specimen with category = lectotype). **Justifying Articles:** [Art. 72](https://code.iczn.org/types-in-the-species-group/article-72-general-provisions/) (general provisions, detailed in `references/16-species-group-types.md`), 74 (lectotype fixation).

### Publication
The bibliographic work. **Attributes:** bibliographic reference, date (with the [Art. 21](https://code.iczn.org/date-of-publication/article-21-determination-of-date/#art-21-1) precision rules — day/month/year or a fallback rounding when incompletely specified), and the work's own availability under [Art. 8](https://code.iczn.org/criteria-of-publication/article-8-what-constitutes-published-work/)/[Art. 9](https://code.iczn.org/criteria-of-publication/article-9-what-does-not-constitute-published-work/) (see `references/03-publication.md`). **Relationships:** one Publication carries many NomenclaturalAct rows (an original description, several type designations, an emendation can all appear in the same work). **Justifying Articles:** 8–9 (publication), 21–22 (date).

### Agent
A person (or, per [Art. 50.1](https://code.iczn.org/authorship/article-50-authors-of-names-and-nomenclatural-acts/#art-50-1), a deemed-anonymous placeholder) who can be an author of a name or act, or the asserter of a taxonomic opinion. **Attributes:** name form for citation, handling for anonymous/inferred authorship ([Rec. 51D](https://code.iczn.org/authorship/article-51-citation-of-names-of-authors/#art-51), advisory only). **Relationships:** many-to-many with NomenclaturalAct (joint authors, [Art. 50.1.3](https://code.iczn.org/authorship/article-50-authors-of-names-and-nomenclatural-acts/#art-50-1-3)) and with ConceptRelationship (the asserting taxonomist). **Justifying Articles:** 50 (authorship rules), 51 (citation, including the "B in A" contributor form of [Rec. 51E](https://code.iczn.org/authorship/article-51-citation-of-names-of-authors/#art-51)).

### NomenclaturalAct
The event record. **Attributes:** act type (establishment, type fixation, justified/unjustified emendation, replacement name, new combination, First Reviser action, reversal of precedence, Commission Opinion/Declaration), date, FK to Publication, FK(s) to performing Agent(s), FK(s) to affected Name(s) (one-to-many for coordination, §3.1; two Names for a new-combination act — the species-group name and the genus it is now combined with, §3.2), a citing-Article field, and free-text effect description. **Relationships:** hub of the whole model — Names, TypeFixations, and Commission overrides all point back to the act that produced them. **Justifying Articles:** 23.6 (priority applies to acts themselves — the first valid act of a given kind wins).

### TaxonConcept
The taxonomic hypothesis: a named circumscription. **Attributes:** FK to the circumscribing Publication and Agent(s), date, rank as applied by this concept (opinion-dependent, distinct from a Name's establishment rank), FK to the Name this concept currently labels as valid, and the set of name-bearing types it includes (defining the circumscription itself, [Art. 61.1.1](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-1-1)). **Relationships:** many-to-many with Name via the included-types set; one-to-one with the Name it currently applies as valid; parent/child to other TaxonConcepts for classification (itself opinion, hence versioned by source). **Justifying Articles:** 23.1/23.3 (valid name is a function of an author's taxonomic judgment applied to the priority rule), 61.1.1 (boundaries vary by opinion; the type-bearing membership is what a concept *is*).

### ConceptRelationship
The asserted (or, for the objective case, derived) link between two TaxonConcepts or two Names. **Attributes:** relation type (subjective synonym, objective synonym, included-in, misapplied, congruent-with), FK to asserting Agent and Publication, assertion date, the rank at which the assertion holds ([Art. 61.3.1](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-3-1) — synonymy at one rank does not imply it at a subordinate rank), and a subtype flag distinguishing *derived* (computed from shared types, never hand-entered) from *asserted* (an opinion, must carry a source). **Justifying Articles:** 61.3 (synonymy and name-bearing types), 23.3 (priority applied to synonymy).

## 3. The hard cases

### 3.1 Coordination (Arts. 36, 43, 46)
One nomenclatural act establishes a name simultaneously at every rank in its group — family/superfamily/subfamily together ([Art. 36.1](https://code.iczn.org/family-group-nominal-taxa-and-their-names/article-36-principle-of-coordination/#art-36-1)), genus/subgenus together ([Art. 43.1](https://code.iczn.org/genus-group-nominal-taxa-and-their-names/article-43-principle-of-coordination/#art-43-1)), species/subspecies together ([Art. 46.1](https://code.iczn.org/species-group-nominal-taxa-and-their-names/article-46-principle-of-coordination/#art-46-1)) — all sharing one author, one date, one name-bearing type, even if the coordinate rank was first *used* by a different, later author. **Consequence:** never store author/date/type as independently-editable scalars copied onto each rank's Name row. Each coordinate Name row carries a FK to the single establishing NomenclaturalAct and (via §61.2.2) the single TypeFixation; author/date/type display is derived by following that FK, so a correction made once propagates to every coordinate rank automatically instead of needing N synchronized edits.

### 3.2 New combination (Art. 48, and the parentheses rule of Art. 51.3)
Combining a species-group name with a genus other than its original one is not a new name — it is a relationship, recorded by [Art. 48](https://code.iczn.org/species-group-nominal-taxa-and-their-names/article-48-change-of-generic-assignment/). **Consequence:** model it as a NomenclaturalAct of type "new combination" linking the (unchanged) species-group Name to a genus-group Name, with its own author/date/publication for the *act of combining*, not for the species-group name itself ([Art. 50.3.2](https://code.iczn.org/authorship/article-50-authors-of-names-and-nomenclatural-acts/#art-50-3-2): combination changes never affect the species-group name's own authorship). The parenthesized author-string customarily printed after a transferred name — e.g. `(Smith, 1850)` — is *derived*: parenthesize the original author/date only when the current genus differs from the name's original combination and that original combination was not itself an incorrect spelling or emendation of the genus name ([Art. 51.3.1](https://code.iczn.org/authorship/article-51-citation-of-names-of-authors/#art-51-3-1)). Storing that parenthesized string as a literal `VARCHAR` field means storing a cached computation that silently goes stale the moment a later reviser publishes another new-combination act. Compute it at render time from the chain: original-combination genus (on Name) vs. current-combination genus (on the latest "new combination" NomenclaturalAct).

### 3.3 Objective vs. subjective synonymy (Art. 61.3)
Same word, two incompatible data shapes. **Objective synonymy** — two nominal taxa sharing (or built on) the same name-bearing type — is a mechanical consequence of the TypeFixation graph ([Art. 61.3.2–61.3.4](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-3-2)): it must be a *computed* relationship (join on shared TypeFixation/TypeSpecimen), never hand-maintained, and it carries no asserting-author field because it is not anyone's opinion. **Subjective synonymy** — nominal taxa with *different* name-bearing types that a taxonomist judges to belong to one taxonomic taxon — is an opinion ([Art. 61.3.1](https://code.iczn.org/the-type-concept-in-nomenclature/article-61-principle-of-typification/#art-61-3-1)) that must always carry the asserting Agent, Publication, date, and the rank at which it holds (it need not hold at a subordinate rank — the rosella-parrot example in Art. 61.3.1 is exactly this). Full treatment in `references/13-typification.md`.

### 3.4 Emendations (Art. 33)
Three outcomes, three storage treatments. A **justified emendation** ([Art. 33.2.2](https://code.iczn.org/formation-and-treatment-of-names/article-33-subsequent-spellings/#art-33-2-2)) corrects an incorrect original spelling and keeps the original author and date ([Art. 19.2](https://code.iczn.org/chapter-4-criteria-of-availability/article-19-status-of-emendations-incorrect-spellings-and-mandatory-changes/#art-19-2)); store it as a corrected-spelling attribute on the *same* Name row, not a new Name. An **unjustified emendation** ([Art. 33.2.3](https://code.iczn.org/formation-and-treatment-of-names/article-33-subsequent-spellings/#art-33-2-3)) is a fully available name in its own right, with its own author and date, a junior *objective* synonym of the name in its original spelling, and it enters homonymy; store it as a genuine new Name row linked to the original by a derived objective-synonym relationship (§3.3) — unless it is in prevailing usage and attributed to the original author/date, in which case Art. 33.2.3.1 deems it a justified emendation after all (a reclassification your model must be able to express without deleting history). An **incorrect subsequent spelling** ([Art. 33.3](https://code.iczn.org/formation-and-treatment-of-names/article-33-subsequent-spellings/#art-33-3)) is *not* an available name and does not enter homonymy or count as a substitute name — but it must still be stored (as a literature-string / spelling-variant record attached to the Name it misspells) so that bibliographic search resolves it, unless it is itself in prevailing usage, in which case Art. 33.3.1 deems it the correct original spelling. Cases of doubt default to "incorrect subsequent spelling", i.e. the more conservative, non-name-creating treatment ([Art. 33.5](https://code.iczn.org/formation-and-treatment-of-names/article-33-subsequent-spellings/#art-33-5)).

### 3.5 Homonymy (Arts. 53.3, 57, 58)
Species-group homonymy is defined relative to *which genus a name is currently (or was originally) combined with* — primary homonymy for names originally combined with the same genus, secondary homonymy for names only later brought into the same genus ([Art. 53.3](https://code.iczn.org/homonymy/article-53-definitions-of-homonymy-in-the-family-group-genus-group-and-species-group/#art-53-3), [Art. 57.3.1](https://code.iczn.org/homonymy/article-57-species-group-names/#art-57-3-1)). **Consequence:** secondary homonymy cannot be a static boolean on a Name row — it is a function of the *current combination* (§3.2) and must be recomputed whenever a new-combination act changes which genus a name sits in. Separately, [Art. 58](https://code.iczn.org/homonymy/article-58-variant-spellings-of-species-group-names-deemed-to-be-identical/) lists roughly fifteen categories of spelling difference (ae/oe/e, i/j, u/v, c/k, single/double consonant, -i/-ii genitive endings, and more) that are *deemed identical* for homonymy purposes provided the words share derivation and meaning — so raw string equality is never the correct homonymy test. Keep both the literal spelling and a normalized comparison key generated by an Art. 58 canonicalization function, plus a human-reviewable flag for "same derivation and meaning", since the derivation check (Art. 58's own caveat, illustrated by *calidus* vs. *callidus*) cannot be automated.

### 3.6 Reversal of precedence (Art. 23.9)
*Nomen protectum* / *nomen oblitum* status is the outcome of a specific published act meeting cited, checkable conditions — not a flag a curator sets because a name "feels" senior-but-forgotten. The act requires the acting author to cite both names, state that the younger is to be treated as valid, and give evidence that the senior has been unused since 1899 and the junior used in at least 25 works by at least 10 authors over at least 50 preceding years spanning at least 10 years ([Art. 23.9.1](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-9-1)–[23.9.2](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-9-2)). **Consequence:** model it as a NomenclaturalAct of type "reversal of precedence", with a FK to both Names, the citing Publication/Agent, and a structured evidence reference; the *nomen oblitum*/*nomen protectum* labels attach to the two Name-participants of that specific act, never as a general-purpose status value settable without a backing act. An erroneous reversal is itself reviewable and must default back to prevailing usage until the Commission rules ([Art. 23.10](https://code.iczn.org/validity-of-names-and-nomenclatural-acts/article-23-principle-of-priority/#art-23-10)) — another reason this must be an auditable act record, not an overwritten field.

### 3.7 Commission actions (Arts. 79–81)
A model that computes validity purely from priority and dates will be wrong whenever the Commission has ruled. Opinions take effect immediately on publication ([Art. 80.3](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-80-status-of-actions-of-the-commission/#art-80-3)) and are to be construed rigidly — an Opinion applies only to the named case, never by analogy to a "similar" one ([Art. 80.5](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-80-status-of-actions-of-the-commission/#art-80-5)). Using the plenary power ([Art. 81.1](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-81-use-of-the-plenary-power/#art-81-1)) the Commission can conserve, totally/partially/conditionally suppress, or give specified precedence to a name, type fixation, or other act. **Consequence:** an Opinion/Declaration must be a first-class NomenclaturalAct subtype with exact FK targets (never fuzzy-matched by name string), and the validity/precedence computation must check for an applicable, unretracted Opinion *before* falling back to ordinary date-based priority. There is also an override-of-overrides ordering to respect: an adopted Part of the [List of Available Names in Zoology](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-79-list-of-available-names-in-zoology/) can itself make a name available or unavailable regardless of Arts. 10–20 ([Art. 79.4.1](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-79-list-of-available-names-in-zoology/#art-79-4-1)–[79.4.3](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-79-list-of-available-names-in-zoology/#art-79-4-3)), and where the List and an Official List/Opinion disagree, the List of Available Names wins unless the Commission rules otherwise ([Art. 80.8](https://code.iczn.org/the-international-commission-on-zoological-nomenclature/article-80-status-of-actions-of-the-commission/#art-80-8)). Do not assume one override table is enough; the precedence order among override instruments is itself part of the model.

### 3.8 A specimen changing type category over time (Art. 74)
A specimen that was one of several syntypes can later be designated the lectotype, which retroactively demotes every other former syntype to paralectotype — automatically, by the act itself, not by a separate curatorial edit ([Art. 74.1.1](https://code.iczn.org/types-in-the-species-group/article-74-name-bearing-types-fixed-subsequently-from-the-type-series-lectotypes-from-syntypes/#art-74-1-1), [74.1.3](https://code.iczn.org/types-in-the-species-group/article-74-name-bearing-types-fixed-subsequently-from-the-type-series-lectotypes-from-syntypes/#art-74-1-3)); once validly made, no later lectotype designation for the same nominal taxon has any validity at all. **Consequence:** "type category" is not an attribute of TypeSpecimen — it is a property of the most recent valid TypeFixation row that references a given (Name, Specimen) pair. Never overwrite the specimen row in place when a lectotype is designated; insert a new TypeFixation event and let the old syntype-designating row stand as history. This is the same principle as §1's act-as-record design applied to a single specimen's biography.

## 4. Anti-patterns

| Anti-pattern | Why it fails |
|---|---|
| One `status` column for both nomenclatural and taxonomic status | Conflates a permanent, opinion-free fact (availability, Art. 10) with a reversible, source-dependent opinion (validity, Art. 23.1) — see `references/dwc-mapping.md` §"nomenclaturalStatus vs taxonomicStatus" |
| Storing only the current binomen | Discards the original spelling/combination the Code actually anchors authorship, priority, and homonymy to (Arts. 11.9.3, 23.1, 50.3.2) — the current name is a query result, not ground truth |
| Normalizing spelling variants away | Destroys the emendation/incorrect-spelling history Art. 33 requires you to be able to answer questions about, and breaks literature-string matching for incorrect subsequent spellings preserved under Art. 33.3.1 |
| A `synonym_of` foreign key with no source | Cannot distinguish objective (derived, Art. 61.3.2–4) from subjective (opinion, Art. 61.3.1) synonymy, and cannot answer "who said so, when, at what rank" |
| Recomputing authorship parentheses as literal text | Caches a value that Art. 51.3 defines relative to the *current* combination — it silently goes stale on the next new-combination act (§3.2) |
| Deleting names deemed invalid | Contradicts Art. 10.6 directly: a name once available remains available and citable forever, regardless of its current validity; deleting it breaks resolution of every historical citation to it |

## 5. Alignment with sibling skills

**Darwin Core Conceptual Model** (`../darwin-core/references/CONCEPTUAL_MODEL.md`) does not itself split name from concept — its `Taxon` class ("a group of organisms considered taxonomically homogeneous; can occupy a rank in a hierarchy") is closest to this file's **TaxonConcept**, not to **Name**. When implementing DwC-CM/DwC-DP, map the `Taxon` table to TaxonConcept and carry the nomenclatural (Name-layer) data as satellite fields or a linked vocabulary (below), rather than assuming DwC's `Taxon` row *is* the nomenclatural record. DwC-CM's `Identification` — an Agent's dated classification of a subject, with multiple Identifications allowed per Organism — is the same "assigned by whom, when, from what evidence" shape as this file's ConceptRelationship, applied to occurrence-level determinations instead of nomenclatural synonymy; reuse the pattern, not the table. See `references/dwc-mapping.md` for the field-level crosswalk.

**TDWG TAG NameThing pattern** (`../skos-xl/SKILL.md`, `../skos-xl/references/SKOS_GUIDE.md` Pattern 2) is the SKOS-XL realization of this file's **Name** entity: a `skos:Concept`/`tnc:NameThing` resource carrying `skosxl:prefLabel`/`skosxl:altLabel` for the name and its spelling variants — the natural home for the Name and incorrect-subsequent-spelling records of §3.4 if this model is published as linked-data vocabulary. Keep TaxonConcept and NomenclaturalAct outside the SKOS layer: they are not controlled-vocabulary concepts, they are dated, sourced, relational records. Note that the botanical `hasBasionym` relationship used in that pattern's own example has no ICZN equivalent — zoology's analogous fact is the original-combination genus on a species-group Name (§3.2, Art. 48); do not import "basionym" terminology into a zoological dataset.

**W3C PROV** (`../DataProvenance/SKILL.md`) is the normative vocabulary for exactly the "must carry an asserting source" requirement that runs through §3.3, §3.4, and §3.6. Model a ConceptRelationship or a reversal-of-precedence NomenclaturalAct as a `prov:Entity` (the assertion itself) `wasAttributedTo` a `prov:Agent` (the taxonomist) and/or `wasGeneratedBy` a `prov:Activity` (the publication event carrying a `prov:generatedAtTime`); use `prov:hadPrimarySource` when a later work merely cites an earlier synonymy claim without re-asserting it independently. This is the concrete PROV-O implementation of every "asserting author, publication, date" field this file specifies.
